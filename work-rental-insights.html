Data and AI system

Rental Insights

A governed data and AI system on public US rental data

Designed, specified and validated by me; built with AI-assisted development.

Public data

View the live project page Read the source code on GitHub

Role Architect & Validator Stack BigQuery, dbt, Python, MCP Status Complete. The code is public on GitHub.

Overview

A tested pipeline loads public rental data (Zillow rent indexes, HUD Fair Market Rents and Census ACS) into BigQuery and models it in dbt from bronze to gold, with data-quality checks on every gold table. An MCP server answers questions with a citation or a refusal, behind read-only SQL guardrails and a 19-risk threat model. A 40-question golden set measures the answers (33 of 40 correct in a blind run), and every build task is tracked against a token budget.

Problem

Zillow, HUD and the Census each publish rental and income data, but they do not share a key for metro areas, so every metro has to be matched before the figures can be compared. Even once the data is joined, an assistant answering questions about it can still guess a column or a number, and a wrong answer delivered with confidence does more harm than no answer.

Why it matters

Rent burden and Fair Market Rents inform decisions by property owners, renters and housing agencies. A system that answers those questions needs to show where each number came from and to refuse when the data cannot support an answer, and the AI behind it must never be able to change the data it reads.

How the data flows

dbt builds each layer, and tests run at every step before the next layer reads it.

  1. SourcesPublic rental dataZillow rent indexes, HUD Fair Market Rents and Census ACS
  2. BronzeRaw rows in BigQueryLoaded as published and counted against the source files
  3. SilverTyped and cleanedZillow metros matched to Census areas by name, plus a seed of overrides
  4. GoldTwo facts and two dimensionsKey and relationship tests on every table
  5. MCP serverQuestions answered from goldThree tools return a cited source or a refusal

A second wall sits under the guardrail: the query identity can read gold and nothing else, and a live test denied CREATE TABLE in 5 of 5 attempts.

The build was governed for cost as well as quality. Every build task carried a token forecast, actual use was measured against it, and a cap handed the decision to continue to me rather than letting a run carry on unattended.

Validation

Data quality checks

dbt runs these tests on every build. The gold-table tests passed 33 of 33 on 2026-10-13, and a later run on the synthetic-company models passed 48 of 48 the same day.

  • Unique, non-null keys PassEvery gold table's key is tested unique and not null.
  • Relationships PassEvery monthly fact row must join to a metro and a month in the dimensions.
  • HUD coverage PassEvery metro area must carry a HUD Fair Market Rent.
  • Match-rate floor PassThe build fails if fewer than 95% of Zillow metros match a Census area, or if any top-100 metro is unmatched.

33 of 40 golden-set questions answered correctly, blind

What was tested
Forty questions with expected answers were answered blind on 13 October 2026 by four AI agents in batches of ten, using only the MCP tools and the answer rules, with no access to the expected answers. A separate grader compared each answer with the key without rerunning any query.
How the expected answers were set
I reviewed and approved all 40 questions and their exact expected numbers on 13 October 2026, measured against the gold tables built that day.
What counted as correct
The status and every number must match the key, and every cited source must exist. A number on a refusal, a wrong number, an error, or a request for clarification where an answer was expected counts as a fail.
What failed
Seven questions failed. Three ended in an error after the answerer guessed a join key, one asked for clarification where an answer was expected, and three had the right content under the wrong status label, because the answer rules never named the no-data status.
What changed after
Unknown-column errors now return a retryable hint that names the column and points to the definition tools, and an offline test covers it. The seven failed questions are still to be rerun blind.
How to rerun it
Ask each question in packs/eval/questions.md in a fresh chat with the packs/qa/PACK.md prompt; the offline fix test is python -m pytest mcp/tests/test_query_gold_errors.py

A 95% match-rate floor for Zillow metros

What was tested
The share of Zillow metros matched to a Census area, and whether any of the 100 largest metros is unmatched.
How the expected answers were set
The floor was set from the measured match of 867 of 910 metros (95.3%) and 99 of 99 of the largest metros, and it leaves room for a few new small metros.
What counted as correct
At least 95% of metros matched and no top-100 metro unmatched.
What failed
No failure is recorded.
What changed after
Nothing is recorded as changed.
How to rerun it

Guardrail limits of 1 GB, 30 seconds and 200 rows

What was tested
The SQL guard in offline tests, which send queries over each limit and queries outside the allowed statements and tables.
How the expected answers were set
Each limit was set for a stated reason. The 200-row cap keeps a response readable in a chat client, the 30-second timeout leaves room over gold queries that took a few seconds, and the 1 GB scan cap stops a runaway scan of gold tables that total a few tens of megabytes.
What counted as correct
The guard refuses every query over a limit or outside the allowed statements and tables.
What failed
No failure is recorded.
What changed after
Nothing is recorded as changed.
How to rerun it
python -m pytest mcp/tests

CREATE TABLE denied in 5 of 5 live attempts

What was tested
The query identity, live against BigQuery, reading gold, trying to create a table in gold and reading silver.
How the expected answers were set
Gold reads allowed, and every write and every silver read denied.
What counted as correct
Each attempt ends as expected, with no table left behind.
What failed
The first attempt failed before the permissions had propagated. After that, gold reads were allowed 5 of 5, CREATE TABLE was denied 5 of 5 and silver reads were denied 5 of 5, with no leftovers. A separate live write-bypass test was also denied 5 of 5.
What changed after
Nothing is recorded as changed.
How to rerun it
python scripts/probe_readonly.py (live BigQuery, with the project's own credentials)

Limitations and lessons

The blind run is a single run of 40 questions, and the fix for the join-key error has been tested offline only, so a fresh blind run is still needed to show the score has moved. The count of 33 of 40 came from a short scoring script that is not kept in the repository, so it cannot yet be rerun with one command. The affordability table stays empty until I decide how the Zillow terms allow its figures to be shown. The build used 5.08 times its token forecast, just over the five-times cap I had accepted, and that overrun is recorded as an open item rather than hidden. The clearest lesson came from the failures, where an error with no usable reason left the answerer guessing, so the server now names the unknown column and points to where to check it.
