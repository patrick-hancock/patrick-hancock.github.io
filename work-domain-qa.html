Grounded Q&A service

Domain Q&A Service

A production AI assistant that answers from the team's own sources or says it cannot

Role: System design, specification and validation • Stack: Python, Claude, MCP, Microsoft Fabric warehouse and OneLake, Power Automate, Jira • Status: In production, with every call logged for cost and answer quality

Staff answering regulatory and process questions used to search three places: a domain dictionary, process documents and the data warehouse. I designed one question service that answers across all three, in a web page or inside a chat client, and treats every answer as a claim it must prove. A sentence without a source is rejected in code before anyone sees it, weak evidence returns "no data" instead of a guess, and generated SQL is checked before it runs. When someone flags a wrong answer, it is routed as a content correction or a software defect.

  • Answer rule Cite or refuse Uncited sentences are rejected in code, not only discouraged in the prompt
  • Answer outcomes 5 statuses Answered, no data, needs clarification, handoff or error, so every refusal is counted

  • New behavior Shadow mode first Changes ship behind flags that default off and run alongside the live path before they replace it

1. How a question is answered

Every question follows one path, whether it comes from the web page or a chat client, and any step can stop it rather than guess.

  1. 01 · Classify Read the question
    Definition, process, live data or a mix; an ambiguous question gets a clarifying reply
  2. ↓
  3. 02 · Retrieve Gather the evidence
    Exact, fuzzy, keyword and meaning-based search over the dictionary and process documents; weak matches return no data
  4. ↓
  5. 03 · Query Ask the warehouse
    SQL generated from the schema and the dictionary's column links, checked by a read-only guardrail and a personal-data screen before it runs
  6. ↓
  7. 04 · Answer Write with sources
    Every sentence carries its source, and an uncited sentence is rejected before the user sees it
  8. ↓
  9. 05 · Learn Close the loop
    Each call is logged for cost and quality, and flagged answers go to a correction or a defect ticket

A selection of the gates that stop a weak or unsafe answer before it reaches the user.

3. Failure handled honestly

When something goes wrong, the service says so plainly instead of guessing.

  • Degrade, don't crash Optional parts fall back to a simpler path when they fail.
  • No internal text leaks Errors reach the user as plain reasons, never as raw system output.
  • Honest status No data or a request for clarification, never a confident guess.
  • Fresh answers A cached data answer is discarded when its tables have newer data.

Monitoring and feedback

Every call is recorded, and wrong answers are caught by people and by the service itself.

Call log:
Every call written to the lakehouse, loaded hourly
User flag:
One click reports a wrong answer; a two-stage check sorts the reason
Self-detection:
A free scan of every answer for error text that should never reach a user

Each logged call carries a usage category, so reports separate real questions from other activity when measuring use and cost.
