Cite-or-Refuse Assistant

A production AI assistant that answers from a team's own sources, or says it cannot

Architect and validator.

Former employer's system, details withheld

Role Architect & Validator Stack Python, Claude, MCP, SQL Warehouse Status Built and used in production at a former employer.

Overview

Staff answering regulatory and process questions used to search three places: a domain dictionary, process documents and the data warehouse. I designed one question service that answers across all three, in a web page or inside a chat client, and treats every answer as a claim it must prove. A sentence without a source is rejected in code before anyone sees it, weak evidence returns "no data" instead of a guess, and generated SQL is checked before it runs. When someone flags a wrong answer, it is routed as a content correction or a software defect.

Problem

Staff answering regulatory and process questions had to search three places, a domain dictionary, process documents and the data warehouse, and then piece the answer together themselves. Each search could turn up something that looked right without showing where it came from.

Why it matters

In regulated work a confident wrong answer is worse than no answer, because someone may act on it before anyone checks it. The service therefore had to prove each claim with a source, or say plainly that it could not answer.

Solution and architecture

  2. Retrieval and SQL
  3. Claim check
  4. Answer or refusal

  • Answer outcomes 5 statuses Answered, no data, needs clarification, handoff or error, so every refusal is counted
  • Wrong answers Routed to a fix A flag becomes a content correction or a defect ticket
  • New behavior Shadow mode first Changes ship behind flags that default off and run alongside the live path before they replace it

How a question is answered

Every question follows one path, whether it comes from the web page or a chat client, and any step can stop it rather than guess.

  1. ClassifyRead the questionDefinition, process, live data or a mix; an ambiguous question gets a clarifying reply
  2. RetrieveGather the evidenceExact, fuzzy, keyword and meaning-based search over the dictionary and process documents; weak matches return no data
  3. QueryAsk the warehouseSQL generated from the schema and the dictionary's column links, checked by a read-only guardrail and a personal-data screen before it runs
  4. AnswerWrite with sourcesEvery sentence carries its source, and an uncited sentence is rejected before the user sees it
  5. LearnClose the loopEach call is logged for cost and quality, and flagged answers go to a correction or a defect ticket

Failure handled honestly

When something goes wrong, the service says so plainly instead of guessing.

  • Degrade, don't crashOptional parts fall back to a simpler path when they fail.
  • No internal text leaksErrors reach the user as plain reasons, never as raw system output.
  • Honest statusNo data or a request for clarification, never a confident guess.
  • Fresh answersA cached data answer is discarded when its tables have newer data.

Validation

Monitoring and feedback

Every call is recorded, and wrong answers are caught by people and by the service itself.

Call log
Every call written to the lakehouse, loaded hourly
User flag
One click reports a wrong answer; a two-stage check sorts the reason
Self-detection
A free scan of every answer for error text that should never reach a user

Each logged call carries a usage category, so reports separate real questions from other activity when measuring use and cost.

Results

The assistant was built and used in production by the staff it was designed for, answering in a web page and inside a chat client. Measured results from that system belong to the former employer and are not shown here, so this page describes how it works rather than how often it was right.

Limitations and lessons

This page shows the design, not measured accuracy, and the code and data stay with the former employer, so nothing here can be rerun. The lesson I carried into my other projects is to treat every answer as a claim that must be proved, which is why Summit, Kestrel Valley and Rental Insights each refuse rather than guess.
