Building a centralized intelligence function.

I established the business intelligence function, then connected seven source systems, shared business definitions and a portfolio of reporting products so executives, managers, frontline staff and sales could work from the same numbers.

The context

The company had no business intelligence function, and departments applied conflicting logic to the same measures. After leading a 16-person operations team, I was promoted to build the function from the ground up.

My role

I was the function: I secured leadership buy-in for a governed data platform, gathered and scoped requirements with each department, designed the models and built every product, with no direct reports.

What changed

Departments aligned on one authoritative rule per measure, recorded in a governed data dictionary. Very wide, open-edit tables were retired and rebuilt as purpose-built data products with role-based access and row-level security, closing a data-integrity and access risk.

Quality

Every major KPI and work-stage milestone has a data-quality control that flags entry errors, and operating counts reconcile to finance records, so a dashboard figure can be traced and challenged.

Connecting to AI

The same semantic layer and data dictionary later grounded the company's natural-language assistant, so its answers came from audited business data rather than from the model's guesses.

Case-Management Data Platform

A governed data foundation built from operational source systems.

A layered SQL warehouse that takes case-management API data from raw landing through typed, historized layers to reporting views, with an audit schema that records every batch, every failed row and every last successful load.

The problem

Case management, worker operations, finance and sales each applied their own logic to shared measures, and legacy sources carried conflicting versions of the same records. Reporting needed one governed foundation between the source systems and every report.

My role

I designed the layer model, the load and orchestration pattern and the audit schema, and I built the loaders and their tests myself, directing AI-assisted development and validating every result.

Architecture

Six layers each do one job, from source access through landing, staging, bronze and silver to gold reporting views. An orchestrator runs each entity in turn, continues past an entity that fails, and logs the failure instead of stopping the whole batch.

Implementation

Landing keeps raw payloads with their batch metadata. Staging types the values and hashes each row so changes are detected rather than guessed, and silver keeps every change as a new version. Gold views are built for a specific use and secured by role.

Validation

Every loader has a paired test. Counts reconcile between layers at each entity's declared grain, because a row that looks duplicated can be legitimate source behavior. Current-row selection is tested directly, after an early run showed a rank that was always 1.

Status and next steps

The core entities are loading and tested; the remaining entities and the full set of gold views are still in progress. Next comes late-arriving-change handling in the delta loads and a dated validation report per entity.

The problem

Government correspondence arrived through more than one channel, at a volume of about 300 items a week. Each item had to be read, judged for whether it mattered, matched to its case and started down the right process, so the review burden grew with the volume.

My role

I designed the workflow, built the intake, interpretation and routing, and set the review rules. It ran in production on a low-code automation platform at a former employer, connected to the case workflow and the revenue-recognition process.

Design choices

High-confidence operational notices proceed automatically. Operational notices that do not meet the confidence threshold are routed to a human reviewer. Only correspondence classified as non-operational is excluded from the case workflow. The model reads and proposes, while deterministic rules route and act, which keeps every consequential step auditable.

Implementation

Email and scanned-mail intake feed a single processing path. The model returns a classification, extracted fields and a confidence grade; workflow rules apply the thresholds, open or update the case, and hand qualifying notices to revenue recognition. Reviewers work from the same extracted fields, so a correction is a confirmation rather than a re-keying.

Results

The workflow handles about 300 government notices a week. About 85% of them are high-confidence operational notices processed automatically, and about 15% are operational notices routed to human review. Missed captures were rare in operation. These are operating estimates, not a measured accuracy score.

Limits and next steps

The figures are estimates from operation rather than a dated measurement. The next steps I would take are a labelled evaluation set to measure classification accuracy per notice type, analytics on review corrections to tune the thresholds, and monitoring that alerts when the review share drifts.

How I build intelligence systems.

Across the projects, five practices make systems easier to trust, operate and improve.

  1. Traceable dataPreserve source context, transformation history and validation so figures can be traced.
  2. Shared definitionsReuse documented business rules instead of redefining measures in each report or assistant.
  3. Controlled accessApply role-based permissions, row-level security and explicit limits on what a system can see or do.
  4. Human oversightRoute uncertain or consequential decisions to people rather than allowing automation to exceed its authority.
  5. Continuous evaluationUse tests, reconciliations, regression checks and cost monitoring beyond initial release.

Building the intelligence function.

Building the BI function meant more than delivering reports: it required setting shared standards, aligning departments, establishing delivery practices and governing the products after release.

01 Direction

  • Secured leadership buy-in for a governed data platform, moving analytics beyond desktop data preparation.
  • Led requirement gathering and scoping with each department, turning questions into specifications, data models and delivery plans.
  • Set the standards the function works to: naming conventions, retired sources and one data dictionary.

02 Delivery

  • Unified the departments' source systems into a single source of truth.
  • Delivered the dashboards and the front-end applications each department works in.
  • Moved routine work into automated, human-reviewed workflows, starting with government notices.

03 Governance

  • Data-quality controls on every major KPI, reconciled to finance records.
  • Role-based access and row-level security on every data product.
  • Human review for uncertain AI output, and token-cost tracking for every AI application by department, model and user.
